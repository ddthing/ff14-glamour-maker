# FF14 Glamour Maker P3-lite 컴포넌트 경계 설계

## 1. 목적

현재 동작과 화면을 유지하면서 큰 UI 컴포넌트에 섞여 있는 상태 변경, 비동기 처리, 표시 책임을 분리한다. 이번 단계는 Zustand나 Web Worker를 도입하지 않는다. 대신 이후 C안으로 전환할 때 UI 컴포넌트를 다시 작성하지 않아도 되는 액션 및 데이터 로딩 경계를 만든다.

## 2. 사용자에게 보장할 호환성

다음 공개 동작과 데이터 형식은 변경하지 않는다.

- 공개 URL 해시 및 프리셋 저장 형식
- `AppState`, `EquipmentPart`, `EquipItem`의 직렬화 결과
- 아이템 및 Facewear의 부위 분류와 KO·EN·JA 원문
- 사진 업로드와 크롭 결과
- 아이템 검색 순위, 결과 제한, 선택 방식
- 공유 링크, 실행 취소, PNG 저장 동작
- 데스크톱·모바일 배치, 캔버스 크기, DOM ID와 접근성 의미

기존 사용자에게 적용되는 변경은 검증된 브랜치를 `main`에 병합한 뒤에만 배포한다.

## 3. 선택한 접근

상태 저장소를 교체하는 대신 현재 `useUrlState`를 단일 상태 소스로 유지한다. 상태 변경은 기능 단위 액션 훅으로 모으고, 큰 컴포넌트는 오케스트레이션 컴포넌트와 표시 컴포넌트로 나눈다.

이 접근은 다음 이유로 선택한다.

- 저장소 교체 없이 결합도를 줄여 회귀 범위를 제한한다.
- 함수형 상태 갱신을 사용해 오래된 상태를 캡처하는 문제를 줄인다.
- 향후 동일한 액션 계약을 Zustand 액션으로 교체할 수 있다.
- 검색 UI가 `loadSearchItems` 계약만 사용하게 해 향후 Worker 구현을 숨길 수 있다.

## 4. 아키텍처

### 4.1 상태 액션 경계

`features/glamour`에 상태 변경 전용 액션 계약과 훅을 둔다. 액션은 전체 `AppState`를 UI에 노출하는 대신 사용자가 수행하는 의도를 표현한다.

예상 액션은 다음과 같다.

- 제목과 제작자 변경
- 부위별 아이템 선택 및 제거
- 염색약 변경
- 전체 장비 초기화
- 원본 및 크롭 사진 반영

모든 액션은 `setState(current => next)` 형태의 함수형 갱신을 사용한다. URL 동기화와 상태 보관 책임은 계속 `useUrlState`에 남긴다.

### 4.2 `ControlPanel` 분리

`ControlPanel`은 기능 훅을 연결하고 현재 탭을 관리하는 오케스트레이터로 유지한다. 다음 표시 책임을 별도 컴포넌트로 분리한다.

- 탭 내비게이션
- 공유·저장 작업 영역
- 공유·프리셋·내보내기·실행 취소 상태 메시지

분리된 컴포넌트는 필요한 원시 값과 이벤트 콜백만 받는다. `AppState` 전체나 `setState`는 받지 않는다.

### 4.3 `ItemSearchInput` 분리

검색 데이터 준비, debounce, 최신 요청 판별, 결과 및 활성 인덱스 상태를 전용 훅으로 이동한다. 입력·목록 UI는 combobox/listbox의 DOM과 키보드 동작만 담당한다.

검색 훅은 현재 `loadSearchItems(slot)` 계약을 사용한다. 향후 Worker를 도입할 때 훅 또는 로더 구현만 교체하고 UI 계약은 유지한다.

### 4.4 `InfoPanel` 분리

`InfoPanel`은 캔버스의 정보 배치를 조합하는 역할만 유지한다. 반복되는 장비 출력과 제목·제작자 표시를 작은 표시 컴포넌트로 분리한다.

각 하위 컴포넌트는 렌더링에 필요한 값만 받고 상태 변경 기능은 갖지 않는다. 캔버스의 1080×900 크기와 현재 줄바꿈·빈 슬롯 처리 방식은 유지한다.

## 5. 데이터 흐름

1. `App`이 `useUrlState`에서 현재 상태와 setter를 얻는다.
2. 액션 훅이 setter를 기능 단위 명령으로 변환한다.
3. 제어 UI는 선택된 상태 조각과 액션 콜백을 받는다.
4. 액션은 함수형 갱신으로 새 상태를 만든다.
5. 기존 URL 동기화가 변경된 상태를 직렬화한다.
6. 캔버스는 현재 상태를 읽기 전용으로 렌더링한다.

검색은 별도 흐름을 사용한다.

1. 포커스 또는 포인터 진입 시 현재 부위 데이터 preload를 시작한다.
2. 검색 훅이 debounce 뒤 `loadSearchItems`를 호출한다.
3. 최신 요청의 결과만 UI에 반영한다.
4. 선택 결과는 장비 선택 액션으로 전달한다.

## 6. 오류 처리

- 검색 preload 실패는 캐시를 비우고 실제 검색에서 재시도한다.
- 실제 검색 실패는 기존 번역된 오류 메시지와 `aria-live` 경로를 유지한다.
- 공유·저장·프리셋 오류는 현재 복구 버튼과 메시지를 유지한다.
- 상태 액션은 저장이나 네트워크 작업을 직접 수행하지 않는다.
- 예상하지 못한 상태는 기존 codec 검증을 우회하지 않는다.

## 7. 테스트 전략

### 단위 테스트

- 각 상태 액션이 의도한 필드만 변경하는지 검증
- 다른 부위와 다국어 이름이 그대로 보존되는지 검증
- 장비 초기화와 사진 반영이 함수형 갱신으로 동작하는지 검증
- 검색 훅이 오래된 요청 결과를 무시하는지 검증
- debounce, 빈 검색어, 오류 및 재시도 경로 검증

### 컴포넌트 테스트

- 탭 전환과 `aria-selected` 유지
- combobox 키보드 이동, 선택, Escape 닫기 유지
- 공유·저장·실행 취소 상태 메시지 유지
- 캔버스의 주무기·보조무기 및 빈 슬롯 출력 유지

### 전체 검증

- `npm test`
- `npm run lint`
- `npm run build`
- 사진 업로드 및 크롭 확인
- 얼굴장식과 각 장비 부위 검색·선택 확인
- 공유 링크 round trip 확인
- PNG 저장 및 오류 복구 확인
- 데스크톱과 모바일 핵심 흐름 확인

## 8. 구현 순서

1. 현재 동작을 고정하는 액션 및 컴포넌트 테스트를 보강한다.
2. 상태 액션 계약과 훅을 추가하고 기존 호출부를 교체한다.
3. `ControlPanel` 표시 영역을 분리한다.
4. `ItemSearchInput`의 검색 상태를 훅으로 이동한다.
5. `InfoPanel`의 반복 표시 영역을 분리한다.
6. 전체 검증과 브라우저 스모크 테스트를 수행한다.

각 단계는 독립 커밋으로 만들 수 있어 문제가 생기면 해당 단계만 되돌릴 수 있다.

## 9. 비목표

- Zustand 도입
- Web Worker 도입
- 디자인 또는 레이아웃 변경
- 검색 알고리즘과 아이템 데이터 변경
- URL 및 프리셋 스키마 변경
- 신규 사용자 기능 추가
- 단순 줄 수 감소만을 위한 과도한 파일 분할

## 10. 완료 조건

1. 표시 컴포넌트가 `setState`를 직접 받지 않는다.
2. 상태 변경은 기능 액션 또는 해당 기능 훅을 통한다.
3. 검색 UI가 데이터 저장 위치나 Worker 존재 여부를 알지 못한다.
4. 기존 URL·프리셋·아이템 무결성 테스트가 그대로 통과한다.
5. 새 액션 및 UI 경계 테스트가 추가된다.
6. 테스트, lint, 프로덕션 빌드와 핵심 브라우저 흐름이 모두 통과한다.
7. 사용자 소유 미추적 파일은 수정하거나 커밋하지 않는다.
