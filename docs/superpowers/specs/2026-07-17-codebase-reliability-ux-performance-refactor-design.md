# FF14 Glamour Maker 안정성·UI/UX·성능 리팩터링 설계

## 1. 배경

FF14 Glamour Maker는 React 19, Vite, TypeScript로 구성된 오프라인 우선 장비 검색·글래머 카드 생성 도구다. 현재 애플리케이션은 약 42,813개 아이템을 8.33 MiB JSON 파일에서 검색하고, URL 해시와 프리셋으로 상태를 공유하며, DOM을 PNG로 내보낸다.

이번 리팩터링은 기존 사용자 흐름과 디자인 방향을 유지하면서 다음 문제를 단계적으로 해결한다.

- 손상되거나 오래된 공유 링크·프리셋의 안전한 복원
- 부위별 아이템 누락과 잘못된 분류 제거
- 한국어·영어·일본어 이름의 무손실 보존
- 키보드·모바일·오류 피드백을 포함한 핵심 UI/UX 개선
- 검색과 PNG 내보내기의 측정 가능한 성능 개선
- 기능별 모듈 경계와 테스트 가능한 상태 변경 API 확립

## 2. 확인된 결함과 위험

### 2.1 잘못된 무기·Facewear 분류

현재 `uiCategory 108`은 Facewear로 취급되지만 로컬 데이터에서 리퍼 무기 카테고리다. 예를 들어 `죽음낫`은 무기 검색에서 제외되고 얼굴 장식 검색으로 통과한다.

Facewear는 일반 `ItemUICategory`로 추정하지 않고 별도 `Glasses.csv` 데이터 원천에서 동기화한다.

### 2.2 결과 제한으로 인한 정상 아이템 누락

현재 검색은 최대 200개 결과를 반환한다. 로컬 데이터에서 `의` 검색은 상의 660개, 하의 820개와 일치한다. 슬롯에 맞는 결과가 200개를 넘으면 정상 아이템도 검색 결과에서 잘릴 수 있다.

### 2.3 언어 데이터 손실 가능성

현재 생성기는 한국어 이름이 있는 레코드만 최종 DB에 남긴다. 신규 패치에서 특정 언어 동기화가 늦으면 다른 언어에는 존재하는 장비가 전체 검색 DB에서 제거될 수 있다.

### 2.4 입력 검증과 오류 복구 부족

URL 디코딩 결과의 검증은 현재 객체 여부만 확인한다. 내보내기는 DOM 이미지 주소를 직접 변경하며 실패 피드백이 `alert`와 콘솔에 의존한다.

### 2.5 테스트 기반 부재

현재 패키지 스크립트에는 자동 테스트가 없다. 구조 변경 전에 링크·프리셋·분류·검색·내보내기의 회귀 방지망이 필요하다.

## 3. 목표와 비목표

### 목표

1. 기존 무버전 `#data=...` 링크와 기존 프리셋을 동일한 상태로 복원한다.
2. 주무기·보조무기·머리·상의·손·하의·발·귀·목·손목·반지·Facewear의 원천 항목이 검색에서 누락되지 않게 한다.
3. KO·EN·JA 이름을 게임 데이터 원문 그대로 보존하고 아이템 ID를 기준으로 결합한다.
4. 모바일과 키보드 사용자가 사진 업로드, 장비 선택, 공유, 저장의 핵심 흐름을 완료할 수 있게 한다.
5. 검색과 내보내기를 기준선과 비교해 개선하고 회귀를 감지한다.
6. 상태·검색·내보내기를 독립적으로 이해하고 테스트할 수 있는 기능 모듈로 분리한다.

### 비목표

- 전면적인 시각 디자인 교체
- Zustand 등 새 전역 상태 라이브러리 도입
- 게임 원문에 없는 번역을 AI나 기계 번역으로 생성
- 측정 근거가 없는 광범위한 메모이제이션
- 신규 백엔드 서비스 도입

## 4. 우선순위와 단계

### P0: 안정성과 데이터 정확성

- 테스트 실행 기반과 핵심 fixture 추가
- 버전이 있는 상태 스키마, 검증, 마이그레이션 추가
- 아이템 데이터 무손실 병합과 슬롯 분류 감사 추가
- 리퍼 무기와 Facewear 분류 수정
- 검색 슬롯 필터를 결과 제한보다 먼저 적용
- PNG 내보내기 준비·복원 경계를 명확히 하고 실패 결과를 구조화

### P1: 핵심 UI/UX

- 탭 의미 구조, 방향키, 포커스 표시, `aria-selected` 적용
- 모달 포커스 고정·복귀, Escape 닫기, 배경 스크롤 차단
- 모바일 고정 높이와 중첩 스크롤 제거
- 입력 오류, 손상된 외부 데이터, 복사·공유·저장 결과를 위치에 맞게 표시
- 비동기 상태를 `aria-live="polite"`로 알림
- 직접 DOM 스타일을 변경하는 마우스 이벤트를 CSS 상태로 이동
- `prefers-reduced-motion`을 반영

### P2: 측정된 성능 병목

- 검색용 정규화 문자열을 데이터 준비 단계에서 한 번 생성
- 슬롯별 인덱스와 정확·접두·부분 일치 점수 사용
- 오래된 검색 요청이 새 결과를 덮지 못하게 취소 또는 세대 번호 적용
- 8.33 MiB 아이템 데이터의 초기 번들 비용을 분석하고 필요 시 지연 로딩 또는 별도 청크로 분리
- PNG 준비 과정의 독립 이미지 작업을 안전한 범위에서 병렬화
- 내보내기 해상도·메모리·소요 시간 기준선을 기록

### P3: 컴포넌트 구조

- `glamour`, `search`, `export`, `canvas` 기능 경계 확립
- 전체 `AppState` 전달 대신 선택된 값과 기능 액션 전달
- 큰 UI 파일을 상태 연결 컴포넌트와 표현 컴포넌트로 분리
- 공유 버튼·입력·모달·상태 메시지를 UI 프리미티브로 정리

## 5. 목표 아키텍처

### 5.1 기능 모듈

#### `features/glamour`

- 현재 상태 스키마와 직렬화 버전
- 외부 `unknown` 데이터 검증
- 무버전·구버전 링크와 프리셋 마이그레이션
- 장비·제목·제작자·이미지 상태 변경 액션
- 직렬화와 역직렬화

#### `features/search`

- 원천 데이터에서 생성된 검색 레코드
- 언어별 표시 이름과 검색용 정규화 이름
- 슬롯·Facewear 분류
- 검색 점수화, 결과 제한, 취소 처리

#### `features/export`

- 캡처 대상 준비와 원래 DOM 복원
- 이미지 준비와 PNG 렌더링
- 모바일 공유와 데스크톱 다운로드
- 단계별 상태와 오류 결과

#### `components/controls`, `components/canvas`, `components/ui`

- `controls`: 사용자 입력과 기능 액션 호출
- `canvas`: 검증된 상태의 읽기 전용 시각화
- `ui`: 버튼, 입력, 모달, 상태 메시지 등 재사용 가능한 표현 요소

### 5.2 데이터 흐름

외부 데이터는 다음 경로로만 애플리케이션 상태가 된다.

1. URL 해시 또는 프리셋을 `unknown`으로 디코딩한다.
2. 필드 타입, 허용 슬롯, 문자열 길이, 숫자 범위를 검증한다.
3. 버전이 없거나 오래된 데이터는 순차 마이그레이션한다.
4. 누락된 필드는 안전한 기본값으로 채운다.
5. 검증된 현재 상태만 UI와 캔버스에 전달한다.

새 링크와 프리셋은 버전을 포함해 기록한다. 읽기는 기존 무버전 형식을 계속 지원한다. 이미지 데이터는 기존 정책대로 URL 직렬화 대상에서 제외한다.

## 6. 아이템·번역 완전성 설계

### 6.1 언어 원문 보존

- KO·EN·JA 원천 레코드는 아이템 ID의 합집합으로 결합한다.
- 배열 위치나 이름으로 언어 레코드를 결합하지 않는다.
- 화면 표시 이름은 원천 문자열을 그대로 보존한다.
- 공백 제거·소문자화 같은 정규화는 별도 검색 필드에만 적용한다.
- 요청 언어 이름이 없으면 다른 원천 언어를 표시하고 언어 fallback임을 UI에 표시한다.
- 누락 이름을 추정하거나 번역하지 않는다.
- 따옴표, 쉼표, 줄바꿈, Unicode를 보존하는 표준 CSV 파서를 사용한다.
- 중복 이름은 허용하되 ID는 고유해야 한다.

### 6.2 슬롯 분류

- 주무기와 보조무기의 원천 카테고리는 명시적으로 관리한다.
- 신규 직업 무기 카테고리를 포함하며, 현재 확인된 `105–111`과 리퍼 `108`을 회귀 fixture로 고정한다.
- Facewear는 `Glasses.csv` 전용 레코드로 생성하고 일반 아이템 분류와 섞지 않는다.
- 허용 목록에 없는 신규 장비 카테고리가 나타나면 동기화를 성공 처리하지 않고 감사 보고서를 생성한다.
- 각 슬롯의 원천 ID 집합과 생성된 검색 ID 집합을 전수 비교한다.
- 슬롯별 개수가 이전 승인 기준보다 비정상적으로 감소하면 동기화를 실패 처리한다.

### 6.3 무기 그룹 B안

제어 패널과 검색에서는 주무기·보조무기 필터를 구분한다. 캔버스에서는 둘을 하나의 무기 그룹 행으로 표시한다.

- 주무기는 기본 행 정보로 표시한다.
- 보조무기는 선택됐을 때만 작은 보조 라인으로 표시한다.
- 보조무기가 없으면 빈 영역을 만들지 않는다.
- 긴 다국어 이름은 최대 2줄과 안전한 줄바꿈 규칙을 사용한다.
- 상태에는 선택적 `offhand` 슬롯을 추가한다.
- 기존 링크의 `mainhand`는 그대로 복원하고, 마이그레이션 시 비어 있는 `offhand` 기본값을 추가한다.
- 행 수는 현재 최대 12개 리듬을 유지해 13번째 전체 행으로 인한 축소를 피한다.

### 6.4 검색 순서

검색은 다음 순서로 실행한다.

1. 현재 슬롯 또는 Facewear 데이터 집합을 먼저 선택한다.
2. 선택된 집합에서 KO·EN·JA 정규화 이름을 검색한다.
3. 정확 일치, 접두 일치, 부분 일치 순으로 점수화한다.
4. 안정적인 보조 정렬을 적용한다.
5. 마지막에 표시 결과 수를 제한한다.

정확한 전체 이름 또는 ID 검색은 넓은 검색 결과 수와 무관하게 해당 항목에 도달해야 한다. 결과가 제한됐음을 UI에 알리고 검색어를 구체화할 수 있게 한다.

## 7. 오류 처리와 UI/UX

### 7.1 오류 유형

- 입력 오류: 해당 필드 아래에 원인과 수정 방법을 표시한다.
- 손상된 링크·프리셋: 안전한 기본 상태로 열고 일부 데이터를 읽지 못했다는 경고를 표시한다.
- 복사·공유 실패: 현재 위치에서 다시 시도할 수 있는 메시지를 표시한다.
- PNG 실패: 실패 단계, 가능한 원인, 다시 저장 액션을 표시한다.
- 데이터 동기화 실패: 누락 ID, 신규 카테고리, 언어별 개수 차이를 보고서에 포함한다.

오류 메시지는 문제만 말하지 않고 다음 행동을 제시한다. 사용자 작업 실패를 `console.error`만으로 끝내지 않는다.

### 7.2 내보내기 상태

내보내기는 `idle`, `preparing`, `rendering`, `sharing`, `saved`, `error` 상태를 가진다. 어느 단계에서 실패해도 다음을 보장한다.

1. 변경한 이미지 주소와 캡처 스타일을 원래 값으로 복원한다.
2. `isExporting` 상태를 해제한다.
3. 실패 단계와 재시도 액션을 UI에 전달한다.
4. 사용자가 공유를 취소한 경우 오류로 과장하지 않는다.

### 7.3 반응형 레이아웃

- 문서 스크롤을 최상위 스크롤 소유자로 사용한다.
- 데스크톱 제어 패널은 필요한 경우 sticky로 유지한다.
- 모바일의 고정 `600px` 패널 높이를 제거하고 콘텐츠 높이를 사용한다.
- 모달과 드롭다운만 제한된 내부 스크롤을 가진다.
- 캔버스는 고정 종횡비를 유지한다.

## 8. 테스트와 검증

### 8.1 도메인 단위 테스트

- 무버전 링크와 각 버전 fixture의 마이그레이션
- 잘못된 타입, 알 수 없는 슬롯, 범위를 벗어난 값 거부
- URL 직렬화·역직렬화 round trip
- Unicode KO·EN·JA 문자열 무손실 round trip
- 리퍼 `108`을 포함한 무기 카테고리 분류
- Facewear가 일반 무기·머리 장비에 섞이지 않음
- 주무기·보조무기 분류
- 정확·접두·부분 일치 우선순위
- 슬롯 필터가 결과 제한보다 먼저 실행됨

### 8.2 데이터 감사 테스트

- 언어별 원천 ID 집합과 생성 DB ID 집합 비교
- 각 슬롯의 원천 ID와 검색 가능 ID 전수 비교
- Facewear 원천 ID와 검색 가능 ID 전수 비교
- 필수 표시 이름·아이콘·카테고리 메타데이터 누락 보고
- 신규 카테고리와 비정상적인 슬롯별 개수 감소 감지
- 모든 누락 항목을 ID와 언어별 이름으로 출력

### 8.3 컴포넌트 테스트

- 검색 입력과 결과 목록의 키보드 탐색
- 탭의 방향키 이동과 선택 상태
- 모달의 초기 포커스, 포커스 고정, Escape, 닫힌 후 포커스 복귀
- 비동기 성공·오류 메시지의 live region
- 무기 그룹의 선택적 보조무기 표시
- 긴 KO·EN·JA 이름과 번역 fallback 배지

### 8.4 E2E 테스트

- 기존 링크 열기 → 장비 변경 → 새 링크 복사 → 동일 상태 복원
- 기존 프리셋 열기 → 수정 → 저장 → 동일 상태 복원
- 각 슬롯과 Facewear에서 대표 fixture 검색·선택
- 주무기와 보조무기를 함께 선택하고 한 행으로 렌더링
- 사진 업로드·자르기·PNG 저장
- 모바일 뷰포트에서 전체 핵심 흐름 완료
- 키보드만으로 장비 선택과 저장 실행

## 9. 성능 측정

최적화 전에 다음 기준선을 기록한다.

- 초기 JavaScript와 아이템 데이터 전송·파싱 크기
- 첫 검색 가능 시점
- 검색 p50·p95 지연과 메인 스레드 장기 작업
- 슬롯 변경 후 첫 결과 시간
- PNG 준비·렌더링·공유 또는 다운로드 단계별 시간
- 대표 캔버스에서 내보내기 최고 메모리 사용량과 실패율

각 최적화는 동일한 fixture와 환경에서 전후 수치를 비교한다. 검색 정확성이나 이미지 품질을 희생하는 변경은 적용하지 않는다.

## 10. 완료 조건

다음 조건을 모두 만족해야 해당 단계를 완료로 본다.

1. 기존 무버전 링크와 프리셋 fixture가 동일한 사용자 상태로 복원된다.
2. 모든 지원 슬롯과 Facewear의 원천 ID가 검색 가능 ID에 포함된다.
3. KO·EN·JA 원문이 아이템 ID에 올바르게 연결되고 임의 번역이 없다.
4. 신규 카테고리 또는 비정상적인 개수 감소가 자동으로 감지된다.
5. 리퍼 무기가 무기 검색에 포함되고 Facewear에서는 제외된다.
6. 넓은 검색어에서 200개를 넘는 일치가 있어도 정확한 이름 검색으로 모든 항목에 도달할 수 있다.
7. 기존 캔버스 행 수를 유지하면서 주무기와 보조무기를 함께 표현한다.
8. 키보드와 모바일의 핵심 E2E 흐름이 통과한다.
9. 내보내기 실패 후 DOM과 UI 상태가 복원되고 재시도가 가능하다.
10. lint, typecheck, build, 단위·컴포넌트·E2E 테스트가 통과한다.

## 11. 구현 제약

- 현재 사용자 소유 미추적 파일은 수정하거나 커밋하지 않는다.
- 기존 공개 URL 형식과 프리셋은 마이그레이션 fixture가 통과하기 전 제거하지 않는다.
- 데이터 원천과 카테고리 변경은 코드 변경과 감사 fixture를 함께 포함한다.
- 구조 이동과 동작 변경을 가능한 한 별도 커밋으로 분리한다.
- 각 단계는 독립적으로 빌드·검증·배포 가능한 상태를 유지한다.
